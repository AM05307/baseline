## 2. 프로젝트별 흐름 (요약)

| | 흐름 | 백테스트와 실전이 같은 코드를 쓰는가 | 모의 | 재시작 시 |
|---|---|---|---|---|
| pysystemtrade [1] | 규칙별 연속 forecast(평균 \|f\|=10, 상한 20) → 고정/추정 가중치(균등 쪽으로 강하게 축소, EWMA 평활) → FDM → 변동성 목표 포지션 → 버퍼(±10%) | 같은 시스템 객체 | — | — |
| freqtrade [2] | OHLCV → `IStrategy` 신호 → pairlist → `stake_amount`·`max_open_trades` → protections → 주문 → `Trade`/`Order` DB | 같은 `IStrategy` 클래스. 체결 가정(다음 봉 시가 등)을 문서로 공개 | `dry_run` + 별도 DB 파일 | `startup_update_open_orders()`가 DB의 미체결 주문을 거래소에서 다시 조회한다 |
| Lean [1·2] | Universe → Alpha(Insight) → Portfolio Construction → Risk → Execution. 각 단계는 교체할 수 있는 모델이다 | 같은 알고리즘 코드. 환경(`backtesting`/`live-paper`)과 BrokerageModel만 바뀐다 | `PaperBrokerage` | `LoadExistingHoldingsAndOrders`(브로커가 기준). 현금을 주기적으로 대사한다 |
| Nautilus [1·2] | 데이터 → 메시지 버스 → Strategy → RiskEngine → ExecutionEngine → 어댑터 → 이벤트 → Cache | 같은 커널. "A live node shares strategy and execution-algorithm code with a backtest" | sandbox | 시작 시와 실행 중에 대사한다. 실패하면 시작하지 않는다(fail closed) |
| 한투 strategy_builder + backtester [1·2] | UI에서 만든 전략 → `.kis.yaml` → backtester가 Lean(Docker) 코드를 생성하고, 실전은 `core/`의 별도 코드 | **명세(YAML)만 공유하고 코드는 따로다**(우리 예전 구조와 같은 이원화) | `env_dv="demo"` 기본 | 주문 영속화·복구 코드를 찾지 못했다 |

국장 적합도:
- Lean의 장 운영시간 DB에 KRX는 선물·지수만 있다 [2].
- Nautilus 공식 어댑터에는 한국 증권사가 없다 [1·2].
- freqtrade는 구조상 불가하다 [2].

- 전문가 단위 40% 상한 [1]
- 자본 사다리 기준을 더 다듬는 일(안전장치 자체는 유지) [1]
- 섀도보다 브로커 구현이 먼저 들어온 순서 [1]
- 관점별 토론(LLM 10회 호출, 테이블 3개; 표본 60건까지 석 달) [2]
- 위험 상태를 각자 다시 계산하는 채점 스크립트 여러 개 [2]

과하지 **않은** 것: 킬 스위치, 대사, 멱등성, 비밀값 처리, 정적 검사. 이 부분은 줄이지 않는다.

## 6. 결론 ① — `weighting.py`의 적중률 기반 가중치 [1]

### 6.1 평가

pysystemtrade의 원칙은 "가중치를 데이터로 맞추지 마라. 맞춰야 한다면 균등 쪽으로 강하게 당겨라"다:
- 가중치 추정은 기본으로 꺼져 있다.
- 추정할 때도 handcrafting을 쓴다.
- shrinkage는 0.9다.
- 결과는 EWMA로 평활한다.

우리 구현을 이 원칙에 비춰 보면:
- 방향 적중률만 보고 크기를 무시한다.
- 고른 다음 배분하므로 승자의 저주에 노출된다.
- CI 하한을 넘는 순간 가중치가 0에서 30%로 뛴다.
- 실제로 2026-10-06 v1은 80점이었는데, 통계 검증 뒤 유의한 신호가 0개가 되어 57.5점이 됐다.
- 60/80 임계값이 가중치 합 단위라서, 가중치가 바뀌면 단계 판정 빈도도 소리 없이 바뀐다.

통계 검증 코드는 진단 도구로 가치가 있다. 문제는 그 결과를 가중치에 자동으로 넣는 연결이다.

### 6.2 대안 — 고정된 정보 출처 그룹 균등 가중치 (권장)

- 방향별로 정보 출처 그룹마다 같은 몫을 주고, 설정 파일에 고정한다. **사람이 명시적으로 바꿀 때만** 바뀐다.
- 전문가 40% 상한은 없앤다.
- 임계값은 "켜진 독립 그룹 수"로 다시 정의한다.
- 통계 검증은 진단으로만 계속 보여준다.
- 대안(안 2): 균등 쪽으로 축소한다(λ ≤ 0.1) + EWMA. 복잡도는 거의 줄지 않는다.
- 평가 지표: 적중률 대신, 그 신호를 넣고 돌린 what_if와 빼고 돌린 what_if의 손익 차이.

**구체안(그룹 구성·각 신호를 넣은 이유·백분위 기준점·기준 설정 구간과 검증 구간 분리)은
[signal_group_weighting_design.md](signal_group_weighting_design.md)에 있다.** 원본의 예시 그룹표는 [archive/reference_gap_analysis.md](archive/reference_gap_analysis.md) 6.2절에 있다.
설계안은 실측 상관을 근거로 그 표를 조정했다(예: KHJ_OVERHEAT와 BOX_RANGE_TRIM을 같은 그룹으로).

## 7. 결론 ② — `what_if.py`와 `planner.py`의 이원화 [1] — **처리됨**

원래 차이:
- D-1 드리프트: what_if는 목표가 바뀔 때만 거래했고, planner는 매일 거래했다.
- D-2 단위: 비율 대 정수 주식.
- D-3 비용: 세 곳에서 각각 계산했다.
- D-4 단계 비중: 두 곳에 있었다.
- D-5 체결 시점.

이 차이들이 섀도 괴리(자동 강등 기준)에 섞인다는 게 문제였다.

처리 결과(2026-10-19):
- `analysis/position_policy.target_quantity`를 what_if(`simulate_shares`)와 planner가 함께 쓴다(D-1·D-2).
- 섀도 대 백테스트는 **정확히 일치**하는지 테스트한다.
- 체결 시점은 양쪽 모두 t+1 시가가 기본이다(D-5).

남은 것:
- D-3 비용 모델의 세부(슬리피지·세율 스케줄)는 섀도 비교 기준에서 단순화돼 있다.
- D-4 단계 비중의 단일 출처는 아직 강제하지 않는다.
- 그 앞 단계(신호→단계)의 복사본 문제는 N-1b(R-3)로 남아 있다.
